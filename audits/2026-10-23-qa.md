## Blocker

### QA-001: Practice setup (onboarding) fails every time with a masked "Unexpected error.", leaving the install with no practice
- **Area:** onboarding
- **URL:** `/dashboard` → sidebar **Practice setup → Get started**
- **Steps:**
  1. Sign in as the new admin on a fresh install.
  2. Click **Get started**, leave **Full Bounded Setup** selected, then click **Confirm**.
  3. Repeat with **Custom Bounded Setup**: paste the base JSON with only `medspaInfo.name` and `storefront.displayName` changed, click **Apply Configuration**, then **Confirm**.
- **Expected:**
  - Setup completes, as E-commerce onboarding does.
  - A Practice, Location, StorefrontSetting, resources, categories and services exist.
  - The dashboard and storefront become usable.
- **Actual:**
  - Both paths fail. `POST /api/graphql` `runMedSpaOnboarding` returns:
    `{"errors":[{"message":"Unexpected error.","path":["runMedSpaOnboarding"],"extensions":{"code":"INTERNAL_SERVER_ERROR"}}],"data":{"runMedSpaOnboarding":null}}`
  - The dialog shows "Setup hit an error. Check the failed item tooltip for details; already-created records are safe to keep." (see QA-004).
  - Afterwards `practices` is `[]`, `locations` is `[]`, `storefrontSettings` is `[]`, and the admin's `practice` is `null`.
- **Why it's a blocker:**
  - Every practice-scoped screen depends on a Practice, and so does the storefront (`storefrontPractice.ts` resolves the single published practice).
  - A new med spa can't get past day zero.
- **Likely cause and files:**
  - `features/keystone/mutations/runMedSpaOnboarding.ts`. In production, `assertOwnedLocalDatabase()` returns `false` because `MEDSPA_LOCAL_RUNTIME_FILE` is unset.
  - So the mutation takes the "real practice" branch (`isolatedLocal = false`): `realPracticeSeed()`, then `Practice.createOne({ isDemo: false })`, then the guarded creates.
  - The runtime tests (`features/keystone/onboarding-runtime.test.ts` and others) only run against the owned local DB, so this production branch looks untested.
  - Keystone masks the thrown `Error`, so the real message is only in the Railway logs. Reproduce locally without `MEDSPA_LOCAL_RUNTIME_FILE`, or read the production log line for this mutation.
  - Also check `guardedOnboardingPracticeCreate` and `hasAuthoritativeOnboardingPractice` (imports at the top of that file), the `pg_advisory_xact_lock` call through `$executeRawUnsafe`, and the `Serializable` interactive transaction on the production Postgres.

### QA-002: Dashboard home, the Models menu and every generic list, item and create route are broken in production
- **Area:** dashboard
- **URL:**
  - `/dashboard`
  - `/dashboard/users`, `/dashboard/roles`, `/dashboard/services`, `/dashboard/practices` (and every other `/dashboard/<list>` route)
  - `/dashboard/resources/create`, which **Resources → New resource** links to
- **Steps:**
  1. Sign in as admin.
  2. Look at the Dashboard home.
  3. Expand **Models** in the sidebar.
  4. Open `/dashboard/users`.
  5. On Resources, click **New resource**.
- **Expected:** As in E-commerce:
  - Home lists the models with counts.
  - **Models** expands to every list.
  - List, item and create pages open.
- **Actual:**
  - Home says "No lists configured. There are no data models configured in your admin interface."
  - **Models** expands to nothing.
  - Every `/dashboard/<list>` route, and `/dashboard/resources/create`, returns **404** and renders "Something went wrong. An unexpected error occurred in the dashboard." The console logs `Dashboard operation failed (details redacted).`
  - Every dashboard page also fires a server action on load that returns `{"success":false,"error":"Unknown error"}`.
- **Evidence:**
  - With the same admin cookie, the exact `KsFetchAdminMeta` query from `getAdminMetaAction.ts`, posted to `/api/graphql` **from the browser**, returns 200 with **no `errors`**. The body is **772,823 bytes**.
  - Small **server-side** `keystoneClient` calls on the same server succeed. The Appointments, Checkout, Commissions, Schedules and Resources pages load real zero counts, and the sidebar and user menu resolve `QA Admin`.
  - So only the large server-side AdminMeta self-fetch fails. Suspect its size or time over the self-fetch to `https://<x-forwarded-host>/api/graphql`, rather than auth.
  - The same symptom is open in the Salon and Barbershop round-1 audits. The code is byte-identical to E-commerce, so the fix probably belongs in the shared baseline.
- **Why it's a blocker:**
  - Several day-one records have no platform screen: users and roles, payment providers, message templates, intake forms, gift cards, locations and the practice itself.
  - The Models section is the only way to reach them, and it's dead.
  - It also breaks **New resource** on a platform page.
- **Likely files:**
  - `features/dashboard/actions/getAdminMetaAction.ts`
  - `features/dashboard/lib/keystoneClient.ts` (`redirect: 'error'`, no timeout handling)
  - `features/dashboard/lib/getBaseUrl.ts`
  - `features/dashboard/screens/HomePage/index.tsx`
  - `features/dashboard/actions/getListByPath.ts`

## Major

### QA-003: A new practice has no way to become bookable: there's no UI to create a practice or location, and production onboarding publishes nothing by design
- **Area:** onboarding / dashboard
- **URL:** `/dashboard/platform/storefront`, `/dashboard/platform/administration`, `/`
- **Steps:**
  1. After QA-001, open **Storefront settings**.
  2. Type a display name and tick **Publish storefront**.
  3. Open **Staff & locations**.
  4. Open the storefront home.
- **Expected:** A merchant can add a location, set the display name and publish, then add treatments, providers and hours so clients can book.
- **Actual:**
  - Storefront settings shows "No active practice location." The location select is empty, and **Save storefront settings** stays disabled. Nothing on the page links to creating a location.
  - Staff & locations shows "Staff & locations unavailable".
  - The generic Location and Practice lists are dead (QA-002).
  - The storefront shows "Not published yet" on every route.
- **Also by design:**
  - When onboarding runs on production (`isolatedLocal = false`), `realPracticeSeed()` forces `storefront.isPublished = false` and makes every resource and service non-public.
  - It also empties providers, schedule blocks, gallery, memberships and packages.
  - So even a **successful** onboarding leaves an unpublished storefront with zero bookable treatments and zero providers. The merchant then has to finish everything on platform screens that can't create those records today.
  - E-commerce onboarding ends with a working store.
- **Likely files:**
  - `features/keystone/mutations/runMedSpaOnboarding.ts` (`realPracticeSeed`)
  - `features/platform/storefront-settings/screens/*`
  - `features/platform/workspaces/screens/MedSpaWorkspacePage.tsx` (the `administration` section)

### QA-007: Logo hue and storefront accent use the same number in two different ways, so the logo and site colours never match
- **Area:** dashboard / storefront
- **URL:** `/dashboard/platform/storefront` (Logo hue slider), storefront shell
- **Steps:**
  1. Open Storefront settings.
  2. Leave Logo hue at 0°, then move it to 120°.
- **Expected:** One hue drives both the logo and the storefront accent, so a "120°" brand is the same colour everywhere. The redesign brief calls this "logo-hue theming".

  - The "120°" readout suggests an absolute hue, and it matches neither.
- **Likely files:**
  - `features/platform/storefront-settings/components/LogoPicker.tsx` (lines 29, 73)
  - `features/storefront/components/StoreBrand.tsx:7`
  - `features/storefront/screens/MainLayout.tsx:17-24` (`theme()`)

### QA-008: The onboarding copy and choices read like an internal compliance spec, not a merchant setup
- **Area:** onboarding
- **URL:** `/dashboard` (Practice setup dialog)
- **Actual:**
  - **Option names and copy:**
    - The options are "Essential Bounded Setup", "Full Bounded Setup" and "Custom Bounded Setup".
    - Their copy includes "fail-closed placeholder seed", "regulated authority and treatment evidence remain unconfigured" and "Customize the medspa seed JSON".
    - The title is spelled "MedSpa Setup", while the product says "Med Spa" everywhere else.
  - **Full vs Essential:** "Full" says it "Uses the same fail-closed placeholder seed". The merchant can't tell what the difference is.
  - **Preview list:**
    - Sections 6 **Patient Records**, 8 **Consumer Contracts** and 10 **Appointment Evidence** are always empty.

    - The sample practice is "Juniper Vale Med Spa — Demo".
  - **Custom path:**
    - The "complete" base JSON holds 1 category, 1 resource and 1 service, while the Full preview shows 2, 3 and 3.
    - Applying it drops the intake and message-template items from the preview.
    - The built-in AI prompt requires the internal name to stay marked "Demo"/"Mock" and `isPublished` to stay `true`. A real practice wouldn't want the first, and production overrides the second (QA-003).
- **Expected:**
  - Plain merchant language, e.g. "Start with sample treatments" vs "Start empty".
  - Steps that each create something, or else are hidden.
  - Names without "— Configuration Required".
  - A custom path that matches the preview.
- **Likely files:**
  - `features/platform/onboarding/config/templates.tsx`
